# خطة تجهيز البناء التلقائي لملف APK على GitHub وتحسين استقرار المعاينة

تهدف هذه الخطة إلى تمكينك من استخراج ملف **APK** جاهز للتثبيت على هاتفك مباشرة عبر متصفح الجوال باستخدام **GitHub Actions** دون الحاجة لجهاز كمبيوتر، مع تسريع الفحص الشبكي الأولي لضمان عمل المعاينة بسلاسة.

---

### مراجعة المستخدم والقرارات المعتمدة

> [!IMPORTANT]
> تم بناء هذه الخطة استناداً إلى إجاباتك المؤكدة:
> - **سبب المشكلة**: عدم ظهور التطبيق في نافذة المعاينة السحابية والحاجة لتجربته كـ APK فعلي.
> - **الحل المطلوب**: تجهيز مسار بناء تلقائي على GitHub لاستخراج ملف APK.
> - **بيئة الاستخدام**: الهاتف والمتصفح فقط بدون كمبيوتر أو Android Studio.

- **توليد APK سحابياً عبر GitHub**: استخدام سير عمل تلقائي (`workflow_dispatch` + `push`) يبني نسخة Debug موقّعة وجاهزة للتثبيت بنقرة واحدة من المتصفح.
- **الإبقاء على الاتصال المباشر ببوابة القناص**: عدم إضافة أوضاع وهمية، والاعتماد على تجربة الـ APK الفعلي على شبكة الواي فاي المحلية مع تحسين سرعة الفحص المبدئي عند التشغيل.

---

### 1. الفكرة العامة ونطاق التنفيذ

- **ما الذي سيتم تنفيذه**:
  1. إضافة سير عمل بناء سحابي تلقائي لنظام أندرويد (CI/CD) على منصة GitHub يقوم بفحص الكود، تشغيل الاختبارات، وتوليد ملف APK موقّع وقابل للتنزيل مباشرة من متصفح الهاتف.
  2. تسريع مهلة الفحص المبدئي للجلسة عند فتح التطبيق (مهلة قصيرة للفحص الصامت الأولي) حتى لا ينتظر التطبيق طويلاً عند تشغيله خارج شبكة الواي فاي أو في المحاكي السحابي.
- **الفئة المستهدفة**: مستخدم الهاتف الذي يدير المشروع عبر المتصفح فقط ويريد تنزيل ملف التثبيت وتجربته مباشرة على شبكة الواي فاي الخاصة براوتر القناص.
- **القيمة الأساسية**: تحويل الكود إلى ملف APK حقيقي مجاناً عبر سحابة GitHub في دقائق معدودة دون الحاجة لأي أدوات تطوير محلية.

---

### 2. تجربة المستخدم والتصميم المرئي

- **تدفق الاستخدام من متصفح الهاتف**:
  1. يتم دفع التعديلات أو رفع المشروع إلى GitHub من داخل AI Studio.
  2. يبدأ سير العمل التلقائي بالبناء فوراً (أو يمكن تشغيله يدوياً من تبويب **Actions** في GitHub عبر زر **Run workflow**).
  3. عند اكتمال البناء بعلامة الصح الخضراء، يظهر ملف **APK** في قسم **Artifacts** (أو في صفحة الإصدارات **Releases**) ليتم تنزيله وفك ضغطه/تثبيته مباشرة على الهاتف.
- **الاستقرار البصري عند فتح التطبيق**:
  - الإبقاء على الهوية البصرية الحالية المستوحاة من Telegram Web بوضعيها الداكن والفاتح وواجهة RTL العربية الكاملة.
  - ظهور شاشة تسجيل الدخول والعدّاد التفاعلي وجدول الباقات فور الفتح دون تأخير أو تعليق ناتج عن انتظار فحص البوابة خارج الشبكة.
  - استمرار التحقق من الإقلاع وعرض العناصر الأساسية عبر اختبارات الواجهة الآلية.

---

### 3. القرارات التقنية والبدائل المدروسة

- **استخدام نسخة Gradle القياسية بدلاً من Gradle Wrapper**:
  - *القرار*: تهيئة سير العمل السحابي باستخدام أداة إعداد Gradle الرسمية بالإصدار **9.3.1** المتوافق مع المشروع.
  - *السبب*: المشروع لا يحتوي على سكريبت التشغيل المحلي الافتراضي (`gradlew`)، لذا فإن تهيئة Gradle مباشرة داخل سير العمل تمنع فشل البناء من الخطوة الأولى.
  - *البديل المستبعد*: مطالبة المستخدم بتوليد ملفات Wrapper يدوياً عبر كمبيوتر، وهو ما يتعارض مع استخدام الهاتف فقط.
- **فك تشفير مفتاح التوقيع التجريبي تلقائياً أثناء البناء**:
  - *القرار*: استخلاص مفتاح التوقيع التجريبي المضمّن بصيغة نصية آمنة في المشروع قبل خطوة التجميع، مع وجود بديل تلقائي لإنشاء مفتاح قياسي في حال عدم توفره.
  - *السبب*: إعدادات البناء تعتمد على توقيع ثابت لنسخة Debug حتى يتمكن الهاتف من تثبيت التطبيق وتحديثه بسلاسة.
  - *البديل المستبعد*: تعديل إعدادات التوقيع الأساسية في المشروع، مما قد يكسر التوافق مع بيئة AI Studio.
- **تخصيص مهلة فحص قصيرة عند الإقلاع الأول**:
  - *القرار*: استخدام عميل شبكي بمهلة اتصال وقراءة قصيرة (~2.5 ثانية) أثناء الفحص التلقائي الأول عند فتح التطبيق، مع الإبقاء على المهلة الكاملة (8–12 ثانية) عند ضغط المستخدم على تسجيل الدخول أو تحديث الحالة.
  - *السبب*: منع بقاء حالة الفحص معلّقة لفترة طويلة عند تشغيل التطبيق في بيئة معزولة أو خارج تغطية الواي فاي المحلية.

---

### 4. البنية التقنية وآلية البناء السحابي *(مرجع تقني)*

```text
┌─────────────────────────┐      Push / Run Workflow      ┌──────────────────────────────┐
│  مستودع GitHub للمشروع  │ ────────────────────────────▶ │   بيئة GitHub Actions (Linux) │
└─────────────────────────┘                               └──────────────┬───────────────┘
                                                                         │
          ┌──────────────────────────────────────────────────────────────┘
          ▼
┌──────────────────────────────┐     ┌──────────────────────────────┐     ┌──────────────────────────────┐
│ 1. تجهيز Java 17 + Android   │ ──▶ │ 2. تجهيز مفتاح التوقيع      │ ──▶ │ 3. تشغيل الاختبارات وبناء   │
│    SDK + Gradle 9.3.1        │     │    (فك تشفير Debug Keystore) │     │    حزمة app-debug.apk        │
└──────────────────────────────┘     └──────────────────────────────┘     └──────────────┬───────────────┘
                                                                                         │
          ┌──────────────────────────────────────────────────────────────────────────────┘
          ▼
┌────────────────────────────────────────┐     تنزيل وتثبيت من متصفح الهاتف     ┌─────────────────────────┐
│ رفع ملف APK في Artifacts / Release     │ ────────────────────────────────────▶ │ هاتف الأندرويد (واي فاي) │
└────────────────────────────────────────┘                                       └─────────────────────────┘
```

- **نموذج البيانات وحالة التشغيل**:
  - **بيئة البناء السحابي**: تعتمد على `Java 17` و `Android SDK` مع تخزين مؤقت لحزم Gradle لتسريع عمليات البناء اللاحقة.
  - **مخرجات البناء**: رفع ملف APK مباشر مع تسمية واضحة، وإرفاقه كـ Artifact صالح للتنزيل المباشر، بالإضافة إلى خيار نشر إصدار (Pre-release/Release) عند التشغيل اليدوي أو إنشاء وسم إصدار لتسهيل التنزيل المباشر بصيغة `.apk` من متصفح الجوال دون الحاجة لفك ملف `.zip`.
  - **تدفق الحالة داخل التطبيق**: عند الإقلاع، ينفذ `ViewModel` فحصاً سريعاً للجلسة عبر مهلة مختصرة، فإذا كان الهاتف متصلاً بالراوتر ينتقل تلقائياً لصفحة الحالة، وإلا يكتمل الفحص الصامت فوراً وتبقى واجهة تسجيل الدخول جاهزة للتفاعل.
